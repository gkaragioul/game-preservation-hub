The mission in one breath

World War 3 is a multiplayer-only shooter. Every time you launch it, it phones home to the publisher's servers to log you in, load your profile, and put you in a match. When those servers switch off on 3 August 2026, the game becomes an expensive paperweight — even though it's installed on your own drive. Stage 1's job was to replace every one of those servers with our own, running on the same PC, so the game can't tell the difference.

◆ In plain English

Think of the game as a phone that only works if it can call five specific numbers. We didn't change the phone — we quietly became all five people it calls, and we answer exactly the way it expects. The game is completely happy, and none of those calls ever leave your computer.

01
Primer

How an online game actually talks

Before you can replace a game's servers, you have to know exactly who it calls, in what order, and what it expects back. Here's the chain — in human terms. Each box became one of our fakes.

The cast, in plain terms

  • Login — proves you're you, hands back an ID card (a “token”).
  • Meta — the filing cabinet: your level, guns, unlocks, loadouts.
  • Hub — the live switchboard that runs the menu and lobbies.
  • Presence — who's online, friends, chat.
  • Match — the actual battlefield simulation (Stage 2).
▚ Under the hood

Tokens are JWTs. A JWT is a signed slip of text: header.payload.signature. The game can't check the signature itself — only the servers can — so it just carries the slip between services. That's the crack we drove a truck through: since we are every service, we sign our own slips with our own key and set them to expire in ten years.

02
Operation 02 · Reconnaissance

Listening in — capturing the protocol

You can't fake a conversation you've never heard. So while the real servers were still alive, we recorded every word the game and the servers exchanged.

We built a “man-in-the-middle” recorder: it sits between the game and the real servers, quietly writing down every request and reply, then passes them along untouched. The game never notices. When the servers die, that recording becomes our script.

◆ In plain English

Imagine wiretapping your own phone to learn exactly what a customer-service line says — every prompt, every pause — so later you can answer identically without the real line existing. That's the recorder. It even blurs out your personal details (Steam ID, real name, tokens) live, so the footage is safe to stream.

▚ Under the hood

The game's network library (libcurl) is configured with bVerifyPeer=false — it accepts any security certificate without checking it. Normally a flaw; for us it's the front door. Our recorder (and later our fake servers) present a home-made certificate and the game trusts it completely. We redirect the server names to 127.0.0.1 (your own PC) via the Windows hosts file.

03
Operation 03 · Substitution

The body double — our own backend

With the script in hand, we built stand-in servers that replay it — and forge the ID cards the game carries between them. First boot to a real menu.

Three small programs now impersonate the entire backend: one for the profile / filing-cabinet layer, one for the live menu switchboard, one for presence. They don't guess — they serve back the exact recordings from Op 02, and hand the game freshly-signed ID cards on demand.

The moment the game accepted our first forged token and loaded its menu from our recordings was the moment “private server” stopped being a theory.

The token trick

When the game asks “log me in”, our server invents an ID card on the spot, signs it with a key we own, stamps it valid for years, and hands it over. The game carries it to the next service — which is also us.

▚ Under the hood

Three tokens flow at boot, all forged by us:

fxToken — the login ID (HS512)
PlayerToken — “you are player 100001” (HS256)
Hub token — “connect to ws://127.0.0.1:8700”

The client never validates these signatures — only servers do, and we replaced the servers. So the secret can be anything and the expiry can be years out.

◆ In plain English

The game is a courier that carries sealed envelopes between offices without ever opening them. We run all the offices and the seal — so we write whatever we like inside, stamp it with our own seal, and the courier faithfully delivers it. Result: it walked all the way to a working main menu.

04
Operation 04 · Loadout

God mode — unlocking everything

Because the profile now comes from our filing cabinet, we can write anything into it — own every item, max every weapon, top rank — all served as if completely normal.

◆ In plain English

Since we're the one telling the game what you own, we simply say “you own all of it, and you're max level.” The game has no way to disagree — it trusts its own filing cabinet, and the filing cabinet is us.

▚ Under the hood

god_profile.py reads the 1,675 item IDs from the unlock tree, writes them all into inventory, sets currency to 999,999,999, maxes weapon levels, and sets the soldier rank to its cap (52) — which is what unlocks all 12 loadout slots.

Operation 05 · The hard wall

Cutting the cord — forever-offline

One guard didn't answer to us: Epic's anti-cheat login. It checked our credentials against Epic's own servers and threw us out. This is how we beat it.

Everything so far relied on the game trusting its own courier. But the anti-cheat system (Epic Online Services) is smarter: it sends your login off to api.epicgames.dev — a real Epic server — to be verified. With a made-up login, Epic said no, and the game crashed. This was the last, hardest wall.

  WW3.log — the crash
EOS Auth TokenGrant → HTTP 401 errors.com.epicgames.eos.auth.external.invalid_token "UserInfo rejected the token" — real Epic refused our made-up login → game crashes

The insight that broke it open

Epic's verification only works if the game can reach Epic. But the address it calls — api.epicgames.dev — is just a name, and we control the phone book. So we pointed that name at our own PC too, and became Epic. Two things had to be true, and both were:

  1. The anti-cheat doesn't pin its certificate. We proved it accepts our home-made certificate for Epic's address — so it talks to our impostor without complaint.
  2. The tokens are verified against a key the game fetches — from a place we now control. So we publish our own key, sign the tokens ourselves, and they check out perfectly.
▚ Under the hood

Epic's tokens are RS256 — signed with Epic's private key, verified with a public key the game fetches by key-id kid: 2022-06-14…. Since the token's issuer is literally https://api.epicgames.dev/auth/v1/oauth — a host we now own — we serve our own public key under that same key-id (a “JWKS” endpoint), sign forged access + ID tokens with the matching private key and a 10-year expiry. The game verifies our forgery against our own key and it passes.

One crash later — a second Epic component (“Connect”) failed because we handed it an empty config — we captured Epic's real config file directly and served it back. After that, the game sailed through.

Operation 06 · Hardening

Mission-ready — the stability fixes

The game reached the menu, but a “lost connection with the communication service” pop-up kept returning. Chasing it down meant fixing three separate background connections.

ChannelWhat was wrongFixResult
Epic presence socketWe answered a WebSocket request with plain text, so it failed and retried foreverComplete the real handshake & hold it openHELD
Hub switchboardWe only replied to heartbeats, never sent our own — the game timed us outSend a heartbeat every 4 secondsSTEADY
Presence (XMPP)We told the game its ID was an old player number — it couldn't reconcile that and resetUse the correct ID; adopt what the client declaresSTABLE
◆ In plain English

The real culprit was mistaken identity. Our presence server kept greeting the player by the wrong name — an ID left over from an earlier capture. The game got confused about who it was, hung up, and reconnected on a loop. Fix the name, and the nagging pop-up vanished for good.

▚ Under the hood

The XMPP bind returned prod-100001 (a stale ID) while the client identified as prod-100001 — stream torn down every ~40 s. Fixed the bound JID, echoed the client's own from=, and added a server-initiated HeartbeatPing every 4,000 ms.

08
Recon · Stage 2

The road to real matches

Stage 1 got you to the menu. Stage 2 is the battlefield itself — and we've already answered the one question that decides whether it's even possible.

A match server is a much bigger build than the menu — a live simulation, not a set of recordings. Before committing, we had to know: is the battlefield traffic readable, or locked behind encryption? We captured gameplay — standing still, walking, running, driving, tank combat — and measured it.

◆ In plain English

Encrypted data looks like pure static — no patterns, nothing to learn from. Readable data has structure you can decode. We measured the “randomness” of the battlefield traffic. If it came back looking like static, Stage 2 would be nearly impossible from recordings alone. It didn't.

Verdict: feasible

The battlefield speaks standard, un-encrypted Unreal Engine 4 “netcode” — and the engine's exact source code is public, so we read the format instead of guessing. Your captures are neatly separated by activity, so we compare “walking” vs “standing” to find exactly which bytes are position, which are aim, and so on.

▚ Under the hood

Match = UDP :7868, stock UE4.21 UNetConnection. Packet sequence numbers visible in byte 0; the StatelessConnect handshake readable from packet #1. No AES, no Oodle compression. A large effort — but a knowable one.

Stage 2 milestones

  1. Handshake — our server completes the UE4 connection so the client stops retrying.
  2. Load into a map — the client drops into an empty world.
  3. Your soldier appears — the first moment you can move around. The real payoff.
  4. Others, vehicles, combat — the long tail; how far we push is a choice, not a wall.
